## 개요

LLM은 사용자가 입력한 내용뿐만 아니라 이전 대화나 제공된 자료 등을 참고하여 답변을 생성할 수 있다.

하지만 AI가 모든 정보를 무제한으로 기억하고 있는 것은 아니다.

AI가 정보를 어떤 범위에서 참고하는지 이해하기 위해서는 **Context(컨텍스트), Context Window(컨텍스트 윈도우), Memory(메모리), RAG**를 구분할 필요가 있다.

## Context란?

**Context는 AI가 현재 답변을 생성할 때 참고할 수 있도록 제공된 정보**를 의미한다.

다음과 같은 대화를 했다고 가정한다.

```text
사용자:
내가 만들 게임은 카페를 운영하는 타이쿤 게임이야.

사용자:
직원 자동 고용 기능도 넣고 싶어.

사용자:
게임 기획을 정리해줘.
```

마지막 질문에는 카페나 직원 자동 고용이라는 내용이 없지만 AI는 앞의 대화를 참고하여 답변할 수 있다.

앞에서 제공된 정보가 현재 답변을 생성할 때 참고할 수 있는 Context에 포함되어 있기 때문이다.

여기서 중요한 것은 **Context에 포함된 정보와 모델이 학습한 정보는 서로 다르다는 점**이다.

Context에 정보가 포함되었다고 해서 AI 모델 자체가 해당 정보를 새롭게 학습한 것은 아니다.

## Context Window란?

모델이 지금까지의 모든 대화를 무제한으로 처리할 수 있는 것은 아니다.

모델에는 한 번의 추론에서 처리할 수 있는 정보량에 한계가 있으며, 이 범위를 **Context Window**라고 한다.

> **Context Window = 모델이 한 번의 추론에서 처리할 수 있는 정보의 범위**

정보량은 일반적으로 Token을 기준으로 계산한다. 모델에 따라 입력과 출력에 사용할 수 있는 Token 한도가 구분될 수도 있다.

개념적으로 Context Window 안에는 다음과 같은 정보가 포함될 수 있다.

```text
┌──────────── Context Window ────────────┐
│                                        │
│  시스템이 제공한 지침                  │
│                                        │
│  이전 대화                              │
│                                        │
│  사용자가 입력한 질문                  │
│                                        │
│  첨부된 코드·문서에서 가져온 정보      │
│                                        │
│  검색 등을 통해 가져온 정보            │
│                                        │
└────────────────────────────────────────┘

                   ↓

                  LLM

                   ↓

                  답변
```

정확히 어떤 정보가 포함되는지는 사용하는 AI 제품이나 시스템의 구현에 따라 달라질 수 있다.

또한 사용자가 입력한 모든 이전 대화가 반드시 Context Window에 포함되는 것은 아니다. AI 제품은 오래된 대화를 일부 제외하거나 요약하는 등 별도의 방식을 사용할 수 있다.

## Context Window가 부족하면 어떻게 될까?

Context Window는 바이브 코딩에서도 중요한 개념이다.

프로젝트 초기에는 다음처럼 파일이 몇 개밖에 없을 수 있다.

```text
index.html
style.css
script.js
```

이 정도 규모라면 AI에게 전체 코드를 제공하기 어렵지 않다.

하지만 프로젝트가 커지면 상황이 달라진다.

```text
프로젝트
├─ 로그인
├─ 회원가입
├─ 결제
├─ 데이터베이스
├─ 관리자 페이지
├─ API
├─ 사용자 페이지
└─ 수십~수백 개의 코드 파일
```

모든 코드와 관련 문서를 매번 AI에게 제공하는 것은 비효율적이며, 경우에 따라 모델이 한 번에 처리할 수 있는 범위를 넘어설 수도 있다.

이 과정에서 AI가 기존 구조를 충분히 참고하지 못하면 다음과 같은 문제가 발생할 수 있다.

- 기존 데이터 구조와 다른 코드를 생성한다.
- 이미 존재하는 기능을 다시 구현한다.
- 서로 연결된 파일을 고려하지 않고 일부 코드만 수정한다.
- 기존 요구사항과 충돌하는 기능을 만든다.

따라서 프로젝트가 커질수록 **AI에게 코드를 작성시키는 능력뿐만 아니라 필요한 정보를 선별해 제공하는 능력**도 중요해진다.

## Context Window가 크면 무조건 좋을까?

Context Window가 크다는 것은 모델이 한 번에 처리할 수 있는 정보의 범위가 넓다는 의미다.

하지만 많은 정보를 입력한다고 해서 AI가 모든 정보를 동일하게 잘 활용한다는 의미는 아니다.

예를 들어 프로젝트를 전달하면서 다음과 같이 요청한다고 가정한다.

> 지금까지 작성한 회의록 200개, 코드 전체, 기획서, 디자인 문서, 고객 문의가 있습니다. 문제를 찾아주세요.

정보는 충분하지만 어떤 자료가 현재 문제와 관련되어 있는지 파악하는 과정 자체가 어려워진다.

LLM 역시 긴 Context 안에 존재하는 모든 정보를 동일하게 활용한다고 보기는 어렵다.

실제로 긴 입력의 처음과 끝에 있는 정보보다 중간에 위치한 정보를 활용하는 성능이 떨어질 수 있다는 연구 결과도 있다.

따라서 **Context Window가 크다고 해서 가능한 모든 정보를 넣는 것이 항상 좋은 방법은 아니다.**

현재 문제를 해결하는 데 필요한 정보를 선별하는 것이 중요하다.

## Memory란?

Context와 함께 혼동하기 쉬운 개념이 **Memory**다.

두 개념을 단순하게 구분하면 다음과 같다.

### Context

> 현재 답변을 생성할 때 모델이 참고하도록 제공되는 정보

### Memory

> 현재 대화 밖에서도 이전 정보를 활용할 수 있도록 AI 제품에서 구현할 수 있는 기능

Memory는 LLM 자체가 모든 대화를 영구적으로 기억한다는 의미가 아니라, **LLM을 사용하는 서비스에서 별도로 구현할 수 있는 기능**으로 이해하는 것이 좋다.

예를 들어 다음과 같은 구조를 만들 수 있다.

```text
사용자 정보
    ↓
별도의 저장 공간에 저장
    ↓
현재 질문과 관련된 정보 검색
    ↓
필요한 정보를 Context에 제공
    ↓
LLM
    ↓
답변 생성
```

따라서 AI 서비스에 사용자의 정보를 기억하는 기능을 만들고 싶다고 해서 반드시 AI 모델 자체를 다시 학습시켜야 하는 것은 아니다.

필요한 정보를 저장하고 다시 불러와 모델에게 제공하는 시스템을 설계할 수도 있다.

실제 서비스에서는 어떤 정보를 저장할지뿐만 아니라 개인정보 보호, 저장 기간, 삭제 기능 등도 함께 고려해야 한다.

## RAG란?

여기서 이전 강의에서 잠시 다뤘던 <strong>RAG(Retrieval-Augmented Generation, 검색 증강 생성)</strong>가 연결된다.

RAG는 필요한 외부 정보를 검색하여 AI에게 제공한 뒤, 해당 정보를 바탕으로 답변을 생성하도록 만드는 방식이다.

예를 들어 회사 내부 문서가 10,000개 있다고 가정한다.

사용자가 다음과 같이 질문한다.

> 우리 회사의 해외 배송 환불 규정을 알려줘.

문서 10,000개를 모두 LLM에게 제공하는 것은 비효율적이다.

대신 다음과 같은 구조를 사용할 수 있다.

```text
사용자 질문
    ↓
관련 문서 검색
    ↓
환불 규정 관련 자료 발견
    ↓
필요한 내용만 Context에 제공
    ↓
LLM
    ↓
답변 생성
```

이것이 RAG의 기본적인 개념이다.

Memory와 RAG는 서로 다른 개념이지만 함께 활용할 수도 있다.

- **Memory:** 이전에 저장한 정보를 나중에도 활용하기 위한 기능
- **RAG:** 필요한 정보를 검색해 답변 생성에 활용하는 방식

예를 들어 사용자별로 저장된 정보를 검색하여 현재 질문의 Context에 제공한다면 Memory 기능을 구현하는 데 검색 기술을 활용할 수 있다.

## Embedding과 RAG의 관계

1강에서 배운 **Embedding**도 여기서 다시 등장한다.

사용자가 다음과 같이 검색했다고 가정한다.

> 다국어 버튼 만들 때 주의할 점

실제 문서에는 정확히 같은 표현이 없고 다음과 같이 작성되어 있을 수 있다.

> 스페인어 번역 이후 버튼 텍스트가 길어져 레이아웃 수정

단순한 문자 일치 검색에서는 두 문장의 관계를 찾기 어려울 수 있다.

Embedding을 활용한 <strong>Semantic Search(의미 기반 검색)</strong>를 이용하면 표현이 다르더라도 의미적으로 관련된 자료를 찾는 데 활용할 수 있다.

이를 RAG와 연결하면 다음과 같은 구조를 만들 수 있다.

```text
사용자 질문
    ↓
질문과 문서의 의미적 특징을 숫자로 표현
    ↓
Embedding 기반 검색 등으로 관련 자료 탐색
    ↓
필요한 자료를 Context에 제공
    ↓
LLM
    ↓
답변 생성
```

실제 RAG에서는 의미 기반 검색뿐만 아니라 키워드 검색이나 두 방식을 결합한 검색도 사용할 수 있다.

또한 LLM 내부에서 Token을 처리하는 Embedding과 문서 검색에 사용하는 Embedding 모델은 역할과 목적이 다를 수 있다.

이를 활용하면 자신의 문서나 회사 자료 등을 기반으로 답변하는 AI 서비스를 만드는 것도 가능하다.

## 바이브 코딩에서 Context가 중요한 이유

프로젝트가 커졌을 때 AI에게 다음과 같이 요청한다고 가정한다.

> 로그인 버튼이 안 되는데 고쳐줘.

이것만으로는 문제를 정확하게 파악하기 위한 정보가 부족하다.

반면 다음과 같이 필요한 정보를 함께 제공할 수 있다.

```text
[현재 문제]

로그인 버튼을 눌러도 로그인이 되지 않는다.

[프로젝트 정보]

웹 서비스이며 현재 A 인증 방식을 사용한다.

[관련 정보]

로그인 관련 파일은 A, B, C다.

콘솔에는 Y 오류가 발생한다.

[제약사항]

기존 데이터 구조는 변경하지 않는다.
```

AI가 현재 문제를 해결하는 데 필요한 Context가 명확해진다.

따라서 바이브 코딩에서는 단순히 프롬프트를 길고 자세하게 작성하는 것보다 다음 능력이 중요하다.

> **현재 문제를 해결하는 데 필요한 Context를 선별하여 제공하는 능력**

## 정리

이번 글에서 기억해야 할 핵심 개념은 다음과 같다.

| 용어 | 의미 |
| --- | --- |
| Context | 현재 답변을 생성할 때 모델이 참고하도록 제공되는 정보 |
| Context Window | 한 번의 추론에서 처리할 수 있는 정보의 범위 |
| Memory | 이전 정보를 이후에도 활용하도록 AI 제품에서 구현할 수 있는 기능 |
| RAG | 필요한 외부 정보를 검색하여 Context로 제공한 뒤 답변을 생성하는 방식 |
| Semantic Search | 단순한 글자 일치가 아닌 의미적 관련성을 이용해 정보를 검색하는 방식 |

전체적인 흐름을 단순화하면 다음과 같다.

```text
사용자 질문
    ↓
필요한 경우 관련 외부 정보 검색(RAG)
    ↓
질문 + 검색 결과 + 기타 Context 구성
    ↓
Tokenization
    ↓
Embedding
    ↓
Transformer
    └─ Attention을 이용한 문맥 처리
    ↓
다음 Token 예측 및 생성
    ↓
답변 생성
```

이 구조에서 RAG는 LLM 내부의 필수 처리 단계가 아니라, **필요한 외부 정보를 모델에 제공하기 위해 추가할 수 있는 시스템 구성 방식**이다.

다음 글에서는 <strong>Context Engineering(컨텍스트 엔지니어링)</strong>을 중심으로 Context Window의 한계를 살펴보고, RAG, DB, API, 프로그램 로직을 활용해 AI가 현재 작업에 필요한 정보를 효과적으로 제공받도록 설계하는 방법을 알아볼 것이다.

## 추가 Q&A

### Q1. Context와 Context Window는 사용자가 만들어가는 것인가?

**Context는 사용자가 영향을 줄 수 있지만 Context Window 자체를 사용자가 만드는 것은 아니다.**

두 개념은 책상에 비유하면 이해하기 쉽다.

```text
Context Window
= 책상의 크기

Context
= 책상 위에 실제로 올라와 있는 자료
```

Context Window는 모델과 시스템이 한 번에 처리할 수 있도록 지원하는 정보량의 한계다.

사용자가 프롬프트를 통해 임의로 크기를 늘릴 수 있는 것은 아니다.

반면 Context에는 사용자가 입력한 질문, 이전 대화, 제공한 코드나 문서 등이 포함될 수 있으므로 **사용자가 Context 구성에 직접적인 영향을 줄 수 있다.**

다만 Context 전체를 사용자가 만드는 것은 아니다.

AI 제품에 따라 시스템 지침, 검색 결과, 첨부 자료에서 가져온 정보 등도 함께 제공될 수 있다.

### Q2. Prompt와 Context의 차이는 무엇인가?

간단하게 구분하면 다음과 같다.

> **Prompt = 모델에 전달하는 입력**

> **Context = 현재 답변을 생성할 때 모델이 참고하도록 제공된 전체 정보**

예를 들어 다음과 같이 입력했다고 가정한다.

```text
나는 Roblox 카페 게임을 만들고 있다.

직원이 자동으로 주문을 처리한다.

가끔 같은 주문이 두 번 처리되는 문제가 발생한다.

중복 실행되는 원인을 찾아줘.
```

이 전체 입력을 Prompt라고 부를 수 있다.

Prompt 안에서도 역할을 구분할 수 있다.

```text
[참고정보]

Roblox 카페 게임
직원이 주문을 자동으로 처리
같은 주문이 두 번 처리되는 문제 발생

[Instruction]

중복 실행되는 원인을 찾아줘.
```

Prompt 자체가 Context의 일부가 될 수 있고, Prompt 안에도 AI가 참고해야 할 정보를 포함할 수 있다.

따라서 Context를 입력하기 위한 별도의 입력 방식이 반드시 존재하는 것은 아니다.

여기서 Prompt는 좁은 의미로 사용자가 입력하는 요청을 가리키지만, 기술적인 문맥에서는 시스템 지침 등 모델에 전달되는 입력 전체를 가리키기도 한다.

### Q3. Prompt를 입력하는 것은 AI를 학습시키는 것 아닌가?

일반적인 AI와의 대화에서 **Prompt를 입력하는 것과 모델을 학습시키는 것은 서로 다른 과정**이다.

일상적으로 AI에게 정보를 알려준 뒤 다음과 같이 표현하기도 한다.

> AI한테 이렇게 학습시켜 놨다.

하지만 기술적으로 말하는 <strong>Training(학습)</strong>과는 다르다.

Training은 데이터를 이용하여 모델 내부의 <strong>Parameter(파라미터)</strong>를 조정하는 과정이다.

단순화하면 다음과 같다.

```text
대량의 학습 데이터
    ↓
Training
    ↓
모델의 Parameter 조정
    ↓
학습된 모델
```

반면 사용자가 Prompt를 입력해 답변을 받는 과정은 <strong>Inference(추론)</strong>에 해당한다.

```text
이미 학습된 모델
        +
Prompt / Context
        ↓
    Inference
        ↓
      답변
```

따라서 일반적인 대화에서는 Prompt를 입력할 때마다 모델 자체를 새롭게 학습시키는 것이 아니다.

이미 학습된 모델이 **현재 제공된 Prompt와 Context를 이용하여 답변을 생성하는 것**이다.

다만 AI 서비스 제공자가 대화 데이터를 별도의 모델 개선이나 학습 과정에 활용하는지는 서비스별 정책과 사용자의 설정에 따라 달라질 수 있다. 이는 현재 대화에서 즉시 추론하는 과정과 구분해야 한다.

### Q4. 그렇다면 Prompt는 어떻게 작성해야 할까?

Context를 입력하기 위한 특별한 문법이 필요한 것은 아니다.

Prompt 안에 문제 해결에 필요한 정보를 함께 제공하면 된다.

예를 들어 바이브 코딩에서는 다음과 같이 구성할 수 있다.

```text
[목표]

Roblox 카페 타이쿤 게임을 만들고 있다.

[현재 구조]

직원이 자동으로 손님의 주문을 처리한다.

[문제]

가끔 같은 주문이 두 번 처리된다.

[관련 정보]

주문 처리는 ServerScript에서 실행한다.
관련 코드는 아래와 같다.

[요청]

중복 실행되는 원인을 찾고 수정 방법을 설명해줘.

[제약]

현재 데이터 구조는 변경하지 않는다.
```

반드시 위 형식을 그대로 사용할 필요는 없다.

중요한 것은 **AI가 문제를 해결하기 위해 필요한 배경정보와 원하는 작업을 구분하여 전달하는 것**이다.

## Prompt, Instruction, Context, Training 정리

마지막으로 네 개념을 구분하면 다음과 같다.

| 개념 | 의미 |
| --- | --- |
| Prompt | 모델에 전달되는 입력 |
| Instruction | AI에게 무엇을 해야 하는지 전달하는 지시 |
| Context | 답변을 만들 때 참고하도록 제공된 전체 정보 |
| Training | 데이터를 이용해 모델 자체의 Parameter를 조정하는 과정 |

예를 들어 다음과 같은 Prompt가 있다.

> 우리 게임은 Roblox 카페 게임이다. 직원 시스템 코드는 아래와 같다. 이 코드에서 중복 주문이 발생하는 원인을 찾아줘.

여기서 Context와 Instruction은 다음과 같이 구분할 수 있다.

### Context

> Roblox 카페 게임이라는 정보, 직원 시스템 코드, 현재 발생하고 있는 문제

### Instruction

> 중복 주문이 발생하는 원인을 찾아줘.

따라서 기술적으로는 <strong>“Prompt를 입력해 AI를 학습시킨다”</strong>보다는 다음과 같이 이해하는 것이 더 정확하다.

> **Prompt와 Context를 제공하여 이미 학습된 AI가 원하는 방향으로 추론하도록 한다.**
