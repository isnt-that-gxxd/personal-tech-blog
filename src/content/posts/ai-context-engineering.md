## 질문

LLM 모델을 사용하는 것은 이미 학습된 모델에 Context와 Prompt를 제공하고 <strong>Inference(추론)</strong>를 통해 답변을 받는 과정이다.

그렇다면 회사 내부 규칙이나 제공해야 할 Context가 너무 많을 경우에는 어떻게 처리할까?

같은 대화 안에서도 이전에 정한 내용을 AI가 정확하게 반영하지 못하거나, 앞에서 A라고 결정했음에도 이후에는 B라고 답변하는 경우가 있다.

Context Window 안에 정보가 존재한다면 AI는 해당 내용을 모두 정확하게 활용할 수 있는 것일까?

## Context Window는 기억을 보장하는 범위가 아니다

**Context Window는 모델이 한 번의 추론에서 처리할 수 있는 Context의 범위**를 의미한다.

중요한 점은 Context Window 안에 정보가 존재한다고 해서 **모델이 해당 정보를 반드시 정확하게 활용한다는 의미는 아니라는 것**이다.

예를 들어 다음과 같이 많은 정보가 Context에 포함되어 있다고 가정한다.

```text
┌──────────── Context Window ────────────┐
│                                        │
│  회사 규칙                             │
│  상품 정보                             │
│  환불 정책                             │
│  배송 정책                             │
│  사용자와의 이전 대화                  │
│  이전 작업에서 결정한 내용             │
│  현재 사용자의 질문                    │
│  ...                                   │
│                                        │
└────────────────────────────────────────┘

                  ↓

                 LLM

                  ↓

               Inference
```

모델은 이 정보를 바탕으로 답변을 생성할 수 있다.

하지만 정보가 많거나 비슷한 내용이 여러 곳에 존재하거나 서로 충돌하는 경우, 필요한 정보를 제대로 활용하지 못할 가능성이 있다.

따라서 다음 두 가지는 같은 의미가 아니다.

> **Context Window가 크다 ≠ 모든 정보를 정확하게 기억한다**

## 같은 대화에서도 이전 내용을 놓칠 수 있는 이유

긴 대화를 계속하다 보면 이전에 결정한 내용을 AI가 제대로 반영하지 못하는 경우가 있다.

예를 들어 앞에서 다음과 같이 결정했다고 가정한다.

> 블로그의 모든 소제목 사이에는 여백을 2줄 이상 적용한다.

이후 수많은 대화와 새로운 지시가 추가된 뒤 다시 블로그 글 작성을 요청하면 AI가 해당 조건을 제대로 반영하지 못할 수도 있다.

이런 현상에는 여러 원인이 있을 수 있다.

- 중요한 정보가 긴 Context 속에 묻혀 있음
- 비슷한 지시가 여러 번 등장함
- 이전 지시와 최근 지시가 서로 충돌함
- 현재 질문과 관련된 정보를 모델이 제대로 활용하지 못함
- AI 서비스가 긴 대화를 처리하는 과정에서 이전 정보를 그대로 제공하지 않는 경우

따라서 단순히 다음과 같이 생각하기보다는

> AI가 기억하지 못했다.

다음 관점으로 접근하는 것이 더 정확하다.

> **현재 추론 과정에서 필요한 정보가 적절한 Context로 제공되고 활용되었는가?**

## 회사의 모든 정보를 Context에 넣어야 할까?

그럴 필요는 없다.

예를 들어 쇼핑몰에 다음과 같은 회사 문서가 있다고 가정한다.

```text
회사 문서
├─ 환불정책.md
├─ 배송정책.md
├─ 개인정보정책.md
├─ 포인트정책.md
├─ 회원정책.md
├─ 상품정책.md
├─ 쿠폰정책.md
├─ 해외배송정책.md
└─ 기타 수천 개의 문서
```

사용자가 다음과 같이 질문한다.

> 해외배송 상품을 환불하고 싶어요.

이 질문에 답하기 위해 회사 문서 전체를 LLM에게 제공할 필요는 없다.

대신 현재 질문과 관련된 자료를 먼저 검색할 수 있다.

```text
사용자 질문
"해외배송 상품을 환불하고 싶어요."
                ↓
          관련 자료 검색
                ↓
     해외배송 정책 + 환불 규정
                ↓
     필요한 내용만 Context에 제공
                ↓
               LLM
                ↓
               답변
```

이처럼 **많은 정보를 모두 제공하는 것보다 현재 문제에 필요한 정보를 찾아 제공하는 것이 중요하다.**

RAG가 활용될 수 있는 이유도 여기에 있다.

## RAG를 이용해 필요한 Context만 가져오기

<strong>RAG(Retrieval-Augmented Generation, 검색 증강 생성)</strong>는 외부 자료에서 현재 질문과 관련된 정보를 검색하고, 해당 정보를 LLM의 Context로 제공한 뒤 답변을 생성하도록 하는 방식이다.

전체 회사 자료를 Context에 넣는 대신 다음과 같이 처리할 수 있다.

```text
회사 문서
    ↓
검색 가능한 형태로 관리


사용자 질문
    ↓
관련 자료 검색
    ↓
필요한 자료 선택
    ↓
Context에 추가
    ↓
LLM
    ↓
Inference
    ↓
답변
```

따라서 RAG는 단순히 Context Window의 한계를 해결하기 위한 방법만이 아니라 **현재 질문과 관련된 정보를 선별해 제공하기 위한 방법**으로도 활용할 수 있다.

다만 검색한 문서가 항상 정확하거나 최신이라는 보장은 없다.

실제 서비스를 구현할 때는 검색 결과의 정확성, 문서의 최신성, 사용자별 접근 권한 등도 함께 고려해야 한다.

## 모든 회사 규칙을 LLM의 판단에 맡기면 안 되는 이유

회사의 문서와 규칙을 검색해서 LLM에게 제공하는 것만으로 충분하지 않은 경우도 있다.

특히 다음과 같은 정보는 정확성이 중요하다.

- 결제
- 환불 가능 여부
- 재고
- 회원 권한
- 할인 금액
- 주문 상태
- 배송 상태

예를 들어 회사 규칙이 다음과 같다고 가정한다.

> 상품 수령 후 7일 이내에만 환불할 수 있다.

LLM에게 해당 규칙을 제공하고 환불 가능 여부를 직접 판단하게 할 수도 있다.

하지만 실제 환불 처리처럼 정확성이 중요한 기능이라면 **일반 프로그램이 조건을 검사하도록 만드는 것이 더 적절하다.**

```text
환불 요청
    ↓
회사 서버
    ↓
환불 조건 검사
    ↓
상품 수령 후 7일 이내인가?
    ↓
YES / NO
    ↓
확정된 검사 결과
    ↓
LLM
    ↓
사용자가 이해하기 쉬운 문장으로 설명
```

위 구조는 원리를 이해하기 위한 단순화된 예시다.

실제 환불 가능 여부는 기간 외에도 상품 상태, 환불 사유, 관련 법규, 예외 규정 등을 종합해 판단해야 할 수 있다.

중요한 점은 **LLM이 모든 판단을 담당할 필요는 없다는 것**이다.

## LLM과 일반 프로그램의 역할을 나누기

실제 AI 서비스는 LLM 하나만으로 구성되는 것이 아니다.

서비스의 목적에 따라 여러 시스템이 함께 동작한다.

```text
                 사용자
                   ↓
                  LLM
                   ↓
           필요한 작업 판단
                   ↓
      ┌────────────┼────────────┐
      ↓            ↓            ↓
   회사 문서    실시간 정보    중요 조건
      ↓            ↓            ↓
   RAG / 검색     API       프로그램 로직
      ↓            ↓            ↓
   정책 검색     DB 조회       조건 계산
      │            │            │
      └────────────┼────────────┘
                   ↓
              필요한 결과
                   ↓
                  LLM
                   ↓
             자연스러운 답변
```

각각의 역할을 구분하면 다음과 같다.

| 작업 | 담당할 수 있는 시스템 |
| --- | --- |
| 사용자의 질문 이해 | LLM |
| 자연스러운 문장 생성 | LLM |
| 관련 회사 문서 검색 | RAG / 검색 시스템 |
| 현재 재고 확인 | DB + API |
| 주문 상태 확인 | DB + API |
| 환불 가능 기간 계산 | 일반 프로그램 로직 |
| 결제·환불 실행 | 회사 서버 |
| 사용자에게 결과 설명 | LLM |

서비스에 따라 LLM이 어떤 API를 호출할지 선택할 수도 있지만, **중요한 작업의 실행 권한과 최종 검증은 신뢰할 수 있는 서버에서 관리해야 한다.**

따라서 **LLM은 AI 서비스 전체가 아니라 서비스를 구성하는 하나의 핵심 요소**라고 볼 수 있다.

## AI 상담원에서는 어떻게 동작할까?

쇼핑몰에 AI 상담원이 있다고 가정한다.

사용자가 다음과 같이 질문한다.

> 지난주에 산 신발을 환불하고 싶은데 가능해?

### 1. 사용자 의도 파악

먼저 LLM이 질문의 의미를 파악한다.

```text
사용자 질문
    ↓
LLM
    ↓
"특정 주문의 환불 가능 여부를
확인하려는 질문"
```

### 2. 주문 정보 조회

이후 회사 시스템이 실제 주문 정보를 조회한다.

```text
주문 DB
    ↓
주문 및 배송 정보 확인
    ↓
배송 완료일: 11월 5일
```

실제 서비스에서는 해당 주문에 접근할 권한이 있는 사용자라는 점도 확인해야 한다.

### 3. 환불 조건 계산

회사 프로그램은 해당 데이터를 이용해 환불 가능 조건을 검사한다.

```text
배송 완료일
    +
현재 날짜
    +
환불 가능 기간
    +
상품 상태와 기타 조건
    ↓
환불 가능 여부 계산
    ↓
YES / NO
```

환불 가능 여부는 실제 날짜와 정책에 따라 달라지므로, 여기서는 특정 결과를 가정하지 않는다.

### 4. 관련 환불 정책 검색

필요하다면 RAG를 통해 관련 환불 정책도 검색한다.

```text
환불 정책
    ↓
단순 변심 가능 여부
상품 미개봉 조건
반품 배송비
예외 규정
```

### 5. 최종 안내 생성

마지막으로 필요한 결과를 LLM에게 제공한다.

```text
주문 정보
    +
서버에서 계산한 환불 가능 여부
    +
관련 환불 정책
    ↓
   LLM
    ↓
사용자에게 설명
```

예를 들어 회사 서버에서 환불 가능 판정을 내렸다면 AI 상담원은 다음과 같이 안내할 수 있다.

> 현재 해당 주문은 환불 신청이 가능합니다. 단순 변심의 경우 반품 배송비가 발생하며, 상품이 개봉되지 않은 상태여야 합니다.

필요하다면 서비스 화면에서 `환불 신청`, `환불 규정 보기` 등의 버튼을 함께 제공할 수도 있다.

이때 실제 환불 신청은 LLM이 임의로 실행하는 것이 아니라, 인증과 권한 검사 등을 거친 서버 기능을 통해 처리하도록 설계해야 한다.

## Context Engineering이란?

이 과정에서 중요한 개념이 <strong>Context Engineering(컨텍스트 엔지니어링)</strong>이다.

단순히 AI에게 좋은 질문을 작성하는 것만으로 복잡한 AI 서비스를 만들기는 어렵다.

AI가 현재 작업을 처리하기 위해 **어떤 정보를 받아야 하는지 설계하는 과정**도 필요하다.

이를 단순하게 비교하면 다음과 같다.

### Prompt Engineering

> AI에게 무엇을 어떻게 요청할 것인가?

### Context Engineering

> AI가 현재 작업을 제대로 수행하려면 어떤 정보를 어떤 구조로 제공해야 하는가?

두 개념은 완전히 분리된 것이 아니라 서로 연결되어 있다.

Prompt Engineering이 모델에 전달할 지시와 요청의 표현에 집중한다면, Context Engineering은 그 요청에 필요한 정보의 선택, 검색, 구성, 전달 방식을 더 폭넓게 다룬다.

예를 들어 AI 상담원의 Context는 다음과 같이 구성될 수 있다.

```text
사용자 질문
    +
상담원의 역할과 핵심 지침
    +
현재 대화에서 필요한 내용
    +
RAG로 검색한 관련 정책
    +
API로 가져온 주문 정보
    +
프로그램이 계산한 환불 가능 여부
    ↓
현재 추론에 필요한 Context
    ↓
   LLM
    ↓
Inference
    ↓
   답변
```

즉 회사가 가진 모든 정보를 LLM에게 제공하는 것이 아니라 **현재 작업에 필요한 Context를 그때그때 구성하는 것**이 중요하다.

## Context Engineering과 Context Window의 관계

두 개념 역시 구분할 필요가 있다.

**Context Window**

> 모델이 한 번의 추론에서 처리할 수 있는 Context의 범위

**Context Engineering**

> 그 범위 안에 어떤 정보를 어떤 방식으로 제공할 것인지 설계하는 것

책상에 비유하면 다음과 같다.

```text
Context Window
= 사용할 수 있는 책상의 크기

Context Engineering
= 현재 업무에 필요한 자료를 골라
  책상 위에 어떻게 배치할 것인지 결정하는 것
```

책상이 아무리 커도 모든 회사 문서를 무작정 올려놓는 것이 항상 좋은 방법은 아니다.

현재 업무에 필요한 자료를 선택하는 것이 중요하다.

## 지금까지 배운 AI 서비스의 구조

지금까지 배운 개념을 하나로 연결하면 다음과 같다.

```text
                  회사 데이터
                      │
          ┌───────────┼───────────┐
          ↓           ↓           ↓
       회사 문서      DB       프로그램 로직
          ↓           ↓           ↓
       RAG / 검색    API        조건 계산
          │           │           │
          └───────────┼───────────┘
                      ↓
사용자 Prompt ──→ 필요한 Context 구성
                      ↓
                Context Window
                      ↓
                     LLM
                      ↓
                  Inference
                      ↓
                    답변
```

LLM은 모든 회사 정보를 기억하는 데이터베이스가 아니다.

**현재 제공된 Context를 바탕으로 추론하여 결과를 생성하는 모델**이다.

따라서 실제 AI 서비스에서는 모든 정보를 LLM에게 기억시키는 것이 아니라 다음과 같은 구조를 활용할 수 있다.

> **저장 → 검색 → 선별 → Context 구성 → 추론 → 결과 검증**

중요한 작업이라면 결과 검증에서 끝나지 않고 서버에서 실제 실행 조건과 사용자 권한까지 확인해야 한다.

## 핵심 정리

- LLM을 일반적으로 사용하는 과정은 **Training이 아니라 Inference**다.
- Context Window는 **모델이 한 번의 추론에서 처리할 수 있는 Context의 범위**다.
- Context Window 안에 정보가 존재한다고 해서 모델이 해당 정보를 반드시 정확하게 활용하는 것은 아니다.
- 회사의 모든 문서를 항상 LLM에게 제공할 필요는 없다.
- 필요한 문서는 RAG 등을 이용해 검색한 뒤 Context에 추가할 수 있다.
- 실시간 재고·주문 정보는 DB와 API 등을 통해 가져올 수 있다.
- 환불 가능 여부처럼 정확성이 중요한 조건은 일반 프로그램 로직에서 처리할 수 있다.
- LLM은 사용자의 질문을 처리하고 여러 시스템의 결과를 받아 자연스러운 답변을 생성하는 역할을 담당할 수 있다.
- 어떤 정보를 언제 LLM에게 제공할지 설계하는 관점을 **Context Engineering**이라고 한다.
- 실제 AI 서비스에서 LLM은 서비스 전체가 아니라 여러 시스템과 함께 사용되는 핵심 구성 요소 중 하나다.

> LLM은 모든 정보를 정확하게 기억하는 데이터베이스가 아니라, 현재 제공된 Context를 바탕으로 추론하는 모델이다. 따라서 실제 AI 서비스에서는 DB, RAG, API, 프로그램 로직 등을 이용해 현재 작업에 필요한 정보를 선별하여 LLM에게 제공할 수 있다.
